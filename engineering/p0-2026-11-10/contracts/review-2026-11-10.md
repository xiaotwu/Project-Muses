## Findings affecting background-next evidence

**P1 — cumulative nonzero output cannot by itself establish a nonzero next item.** In the reviewed `audio/probe.cpp` lines 208 and 217–225, transitions advance on the output clock, nonzero frames are cumulative across A/B, and empty frames from a done input do not count as underflow. The reviewed `source/iOSMain.m` line 85 publishes cumulative counters without transition boundaries. Thus `transitions == 1`, `next_consumed_frames > 0`, `nonzero_output_frames > 0`, `underflow_frames == 0` can all hold when A produced sound earlier and B contains only silence. This is an evidence hole, not a conclusion that a particular observed run was silent.

Required interpretation/measurement: record `transition_start_frame` and `transition_end_frame`; use two snapshots whose output clocks are strictly after the fade end, from the same run/session while the app remains backgrounded. Require unchanged first-input consumption, increasing next-input consumption and increasing nonzero-output frames between those snapshots. Also check decoder errors, stop state and generation identity. An equivalent explicit next-only nonzero-contribution counter is acceptable. This proves nonzero PCM submitted by the native callback, not human audibility or the physical device's speaker output.

Status: reviewed source candidate `75c18082064f0eb09fc6cb83ef8c76fdde3b078b3b7b1fe107bacfdb2d8c2292` now logs both transition boundaries with consumed/nonzero counters. The coordinator will enforce the two-snapshot delta condition. Runtime evidence assessment remains **pending**; existing cumulative-only evidence must not be retroactively described as satisfying this stronger condition.

**P1 — delayed callbacks are not bound to their originating run.** In the reviewed `source/iOSMain.m` lines 77–78, the 30-second Next and 90-second Stop blocks capture only the controller. Stop followed by a new Start leaves the old blocks able to resolve the new session's next item early or stop that new session. This can contaminate repeated-run background measurements.

Minimal correction: give each run a generation, capture it in delayed Next/Stop and remote-command handlers, and validate it on the serial worker immediately before touching audio/current-run state. Invalidate the generation on explicit stop and replacement. Check any asynchronous media-session UI cleanup against its own run so stale cleanup cannot clear a replacement's controls. A fresh-process single uninterrupted run avoids the specific old-callback contamination but does not replace the code fix.

Status: reviewed candidate `75c18082064f0eb09fc6cb83ef8c76fdde3b078b3b7b1fe107bacfdb2d8c2292` captures/checks generations for delayed Next/Stop, snapshot timer and remote handler. Next's delay starts after native audio startup and is scheduled on the serial worker. This addresses the originally identified old delayed-callback action on a replacement session. No parallel edits were made to audio/source files.

Candidate limitation reported to source/coordinator: `acceptMedia` checks generation before, but not after, blocking native start/prepare. An explicit Stop during that call can still return/log an obsolete native start before the queued stop disposes it. `record:` also stamps the current generation on source events still unwinding from the prior execution. Add a post-call identity check (dispose a newly returned stale first session) and origin-bound/suppressed stale log events before claiming cancellation/restart correctness. The candidate is suitable for the intended **fresh-process, single uninterrupted calibration run** with the delta acceptance above; this assessment does not require expanding the user's waiting runtime session into cancellation/restart testing.

Within the single-run flow inspected, snapshot, prepare and explicit stop use the same serial worker and the native ABI documents that serialization requirement. No direct use-after-free was identified on that path. This does not claim the raw-pointer ABI is safe against arbitrary concurrent/destruction calls.

## Contract corrections applied

- Preparation now retains exactly one visible control set for the current sound owner. Play/pause and volume remain usable while video prepares; the new video cannot independently play before the acknowledged ownership transfer. Provider-control suppression applies after it receives playback ownership.
- Sound handoff is separated from navigation completion. User Close, Return to audio and destination-driven dismissal carry their own target route, navigation generation and focus return. A Settings navigation cannot run User Close's browse-return action, and a late acknowledgement cannot restore an obsolete route.
- Official-player visibility rules now apply to expanded, compact and fullscreen placements, including complete sheet occlusion. Losing desktop focus/active status alone does not pause a video that remains visible.

These changes clarify [the embedded-video implementation contract](embedded-video-interaction.md); they are not rendered UI or runtime handoff evidence. Other proposed interaction defaults remain explicitly identified as P0 proposals.
